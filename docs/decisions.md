# Decisions

Dated decisions for this repo, newest last.

- 2026-11-09: created from the standard repo starter kit.
- 2026-11-09: design approved, with three additions that are now built and tested:
  1. **No self-approval.** An approver who is in the set, or who signed in as an account in it, is refused. The owner's own links need another approver.
  2. **Revocation is immediate.** Unlinking (self-serve), an approver deleting a row, an account losing a hat, or an account being deleted removes the Payload session of every session switched into or through it. The set is also re-checked on every request, so a switched session ends even if a revocation was missed.
  3. **Who sees the switch.** Only when the account, or another account in its set, has more than one hat. Where the switch isn't shown, switching is refused too.
- 2026-11-09: defaults: at most 4 accounts in a set; a second factor is remembered for 3 hours per account (`stepUp.rememberMinutes`); confirmation links last 24 hours.
- 2026-11-09 (build): **hat state lives on the server, not in a cookie.** The design note had a signed `hats-wearing` cookie. Built instead: a `hat-sessions` record keyed by Payload's session id. Nothing in the browser can be forged or deleted to change the hat, and revoking means removing Payload's own session.
- 2026-11-09 (build): **a plain sign-in wears all the account's roles**, as before the plugin. Hats narrow from there; switching back up into a sensitive hat asks for the second factor. A session switched into another account starts in the hat chosen at the switch. A stored hat the account no longer holds falls to the narrowest, never the widest.
- 2026-11-09 (build): **the second factor is the target account's.** Switching into account B's sensitive hat asks for B's code, remembered per account.
- 2026-11-09 (build): **approval uses Payload's own admin form.** Approvers set a confirmed row's status to Approved; a hook refuses every other change. Deleting the row unlinks.
- 2026-11-09 (build): **a link request never says whether the other account exists**, is already linked, or is the requester's own: the answer and status are always the same.
- 2026-11-13: moved to the ExtantApe GitHub organization and the `@extantape` npm scope at the same version. EXTANT APE owns its reusable tools and licenses them to the platform. The earlier package name is deprecated with a pointer here, and GitHub redirects the old repository address.
- 2026-11-16 (owner): **going down needs no code, going up does.** "If you're already authenticated on a domain you should be able to go down without 2FA, just not up. If your perms increase, you do 2FA. If they decrease, then no biggie." Sideways counts as up. Two-step is one per person across the linked set, and the 3-hour remembered window stays. The plugin gives the site the means (`stepUpWhen`, `stepUp.rememberPer`, `signedIn` and `set` on the checks); the site decides what counts as holding more. Defaults keep the earlier behavior.
- 2026-11-26 (EXTANT APE Head of Tools ruling): **`switchSession` for a site's own route, as 0.4.0.** One shared core serves the endpoint and the function. No skip options, a typed result, hook errors refuse, and the site switches only from a same-origin POST because SameSite=Lax sends the cookie on top-level GETs. One code per sitting uses `stepUpWhen` with `stepUp.rememberPer: 'set'`; the plugin offers no first-entry-ever mode, since the expiry is the point. Going back down to the signed-in account needs no code while the link is approved and `blocked()` allows it.
- 2026-11-27: **a link request answers the same way whatever the address.** The asker learns nothing about the address from the answer, their own email, what they can read, the writes made for them or the time taken. How: one `hat-requests` record for every request, readable only by the plugin, with a token that works only when an invitation was sent; a short note to the asker that leaves out the address and carries no token; an invitation only to an account that can be linked; and a fixed answer time, `linkAnswerMs` (default 2000), with the work raced inside it. Nothing joins a set until the invited account confirms; then the asker confirms from their own email and an approver reviews, as before. Accounts are treated the same whatever their state or age. Fails closed: request tokens work once and expire with `confirmHours`, a failed invitation's token is cleared, a confirmation is refused if the account joined another set or the set would pass `maxLinked`, and approval refuses past `maxLinked` too. Chosen over sending the asker's confirmation with the request (it shows the target exists), over stateless signed tokens (they can't be used only once) and over reusing `hat-sessions` (a different lifetime and clean-up). What still differs, by design: the invitation is one more email send for a real account, so a mail server's logs see it, and work past `linkAnswerMs` finishes after the answer.
