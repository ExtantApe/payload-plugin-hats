# Decisions

Dated decisions for this repo, newest last.

- 2026-11-09: created from the standard repo starter kit.
- 2026-11-09: design approved, with three additions that are now built and tested:
  1. **No self-approval.** An approver who is in the set, or who signed in as an account in it, is refused. The owner's own links need another approver.
  2. **Revocation is immediate.** Unlinking (self-serve), an approver deleting a row, an account losing a hat, or an account being deleted removes the Payload session of every session switched into or through it. The set is also re-checked on every request, so a switched session ends even if a revocation was missed.
  3. **Who sees the switch.** Only when the account, or another account in its set, has more than one hat. Where the switch isn't shown, switching is refused too.
- 2026-11-09: defaults: at most 4 accounts in a set; a second factor is remembered for 3 hours per account (`stepUp.rememberMinutes`); confirmation links last 24 hours.
- 2026-11-09 (build): **hat state lives on the server, not in a cookie.** The design note had a signed `hats-wearing` cookie. Built instead: a `hat-sessions` record keyed by Payload's session id. Nothing in the browser can be forged or deleted to change the hat, and revoking means removing Payload's own session.
- 2026-11-09 (build): **a plain sign-in wears all the account's roles**, as before the plugin. Hats narrow from there; switching back up into a sensitive hat asks for the second factor. A session switched into another account starts in the hat chosen at the switch. A stored hat the account no longer holds falls to the narrowest, never the widest.
- 2026-11-09 (build): **the second factor is the target account's.** Switching into account B's sensitive hat asks for B's code, remembered per account.
- 2026-11-09 (build): **approval uses Payload's own admin form.** Approvers set a confirmed row's status to Approved; a hook refuses every other change. Deleting the row unlinks.
- 2026-11-09 (build): **a link request never says whether the other account exists**, is already linked, or is the requester's own: the answer and status are always the same.
- 2026-11-13: moved to the ExtantApe GitHub organization and the `@extantape` npm scope at the same version. EXTANT APE owns its reusable tools and licenses them to the platform. The earlier package name is deprecated with a pointer here, and GitHub redirects the old repository address.
- 2026-11-16 (owner): **going down needs no code, going up does.** "If you're already authenticated on a domain you should be able to go down without 2FA, just not up. If your perms increase, you do 2FA. If they decrease, then no biggie." Sideways counts as up. Two-step is one per person across the linked set, and the 3-hour remembered window stays. The plugin gives the site the means (`stepUpWhen`, `stepUp.rememberPer`, `signedIn` and `set` on the checks); the site decides what counts as holding more. Defaults keep the earlier behavior.
- 2026-11-26 (EXTANT APE Head of Tools ruling): **`switchSession` for a site's own route, as 0.4.0.** One shared core serves the endpoint and the function. No skip options, a typed result, hook errors refuse, and the site switches only from a same-origin POST because SameSite=Lax sends the cookie on top-level GETs. One code per sitting uses `stepUpWhen` with `stepUp.rememberPer: 'set'`; the plugin offers no first-entry-ever mode, since the expiry is the point. Going back down to the signed-in account needs no code while the link is approved and `blocked()` allows it.
- 2026-11-27: **a link request answers the same way whatever the address.** The asker learns nothing about the address from the answer, their own email, what they can read, the writes made for them or the time taken. How: one `hat-requests` record for every request, readable only by the plugin, with a token that works only when an invitation was sent; a short note to the asker that leaves out the address and carries no token; an invitation only to an account that can be linked; and a fixed answer time, `linkAnswerMs` (default 2000), with the work raced inside it. Nothing joins a set until the invited account confirms; then the asker confirms from their own email and an approver reviews, as before. Accounts are treated the same whatever their state or age. Fails closed: request tokens work once and expire with `confirmHours`, a failed invitation's token is cleared, a confirmation is refused if the account joined another set or the set would pass `maxLinked`, and approval refuses past `maxLinked` too. Chosen over sending the asker's confirmation with the request (it shows the target exists), over stateless signed tokens (they can't be used only once) and over reusing `hat-sessions` (a different lifetime and clean-up). What still differs, by design: the invitation is one more email send for a real account, so a mail server's logs see it, and work past `linkAnswerMs` finishes after the answer. Follow-up the same day: one open invitation per account from all askers, so no one can fill an inbox; `hat-requests` refuses writes from server code too; deleting the invited account empties its requests without freeing the asker's limit; a confirmation is refused when the asker's set changed since the request, unless the asker started that set from another of their own requests; and `link-requested` keeps a real set id, firing at confirmation when the asker had no set, so 0.4.0 handlers keep working. Review round two, the same day: the one-invitation rule moved from a count before the write to a unique `holds` key in `hat-requests`, so the database keeps it under concurrent requests on MongoDB and SQL alike; every request now writes a create then a claim, so the writes match whatever the outcome. The plugin's mark on its own writes moved from a `context` key to a map private to its modules, keyed by the request (Payload drops a `context` that holds only symbol keys, so a symbol key wasn't enough). An `onEvent` handler that throws during a confirmation is logged by error name and skipped. Whether to add an age check for linking is an open question for the owner.
- 2026-11-27 (review round three): **ids keep the account collection's own type.** Every relationship the plugin writes (requests, sets, member rows, and the lookups on account delete) uses the users collection's id type, so linking works on SQL databases, where ids are numbers; 0.4.0 wrote strings there and no invitation was ever sent. Rows that point at an account were moved to a `beforeDelete` hook (replaced in round four, below). The site's callbacks (`confirmURL`, `sendEmail`, `onEvent`) run with the plugin's mark off the request. The confirm page waits at most 2 seconds per link event handler and logs only a short safe error name. Left as documented limits: no startup check for the `holds` index when `autoIndex` is off, no support for calling the link handler inside a caller's own transaction, and a stranger's request can hold an account's one invitation until `confirmHours` runs out.
- 2026-11-27 (review round four): **account clean-up runs after the delete, one account at a time, and handlers can't block it.** The round-three `beforeDelete` changed link records even when the delete then failed: Payload runs a bulk delete's documents side by side and commits the ones that succeed, and without a transaction nothing is undone. Chosen instead, as the smallest design that holds on MongoDB with and without transactions, with `disableTransaction`, on SQLite and in bulk: the clean-up is the users `afterDelete`, placed first, so it runs only for a delete that happened; the two required account columns (`hat-members.user`, `hat-requests.requestedBy`) are nullable in the database and required by a field validator on every write, so a SQL foreign key can set them to null and the plugin removes those rows straight after; a per-request queue runs each account's clean-up in turn, so a bulk delete of several accounts in one set leaves nothing behind. Every `onEvent` call except `switched` and `link-approved` goes through one bounded, catching path, so no handler can fail or undo an account delete. The plugin's marks moved from a per-request map to an async context: a mark holds only for the plugin's code and what it awaits, so a site callback can't leave it on or see it. Unlink takes only an exact id. Known limit: a database failure during the clean-up, without a transaction or in a bulk delete, can leave some rows.
- 2026-11-27 (review round five): **0.5.0 asks nothing of a MongoDB host, and a failure is never reported as done.** The requirement for this release is no disruption to a host on 0.4.0. So the account fields on `hat-members` and `hat-requests` stay `required` on MongoDB, which keeps every 0.4.0 index exactly as 0.4.0 built it (a test starts this build with `ensureIndexes: true` on a database with 0.4.0's indexes); only SQL adapters relax NOT NULL, with the write-time check kept. Every bulk delete or update in the plugin's clean-up throws on any row Payload couldn't handle, because Payload's bulk calls return such errors quietly and, on MongoDB with transactions, after the transaction has already ended. A switched session checks that its signed-in account still exists and is ended if it doesn't. Hooks that aren't the plugin's own run with the mark off. Switch refuses anything but an exact id with its usual `notLinked`, rather than adding a new reason. SQLite push mode can't move a 0.4.0 schema (it stops on the existing `hat_members_link_idx`); that isn't a cheap fix in the plugin, so the host steps say to use a migration.
