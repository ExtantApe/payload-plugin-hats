# Changelog

## 0.4.1 (Unreleased)

- **A link request answers the same way whatever the address.** Whether the address has an account, or that account is locked, unverified, already linked, waiting on another request or the asker's own, the asker sees the same 202, gets the same short note by email (with no token and without the address), can read the same records, and the request makes the same database writes and takes the same time. Only an account that can be linked, and that has no invitation open already, gets an invitation, so an account gets one at a time from all askers together. The database keeps that rule: each request has a unique `holds` value, which is the account while its invitation is open, so of requests that arrive together only one can hold it. Every request makes the same two writes, a create and then that claim. Nothing joins a set until that account confirms: then the asker gets their own link to confirm, and an approver reviews as before.
  - **New `hat-requests` collection** holds open requests. Access is closed to every user, so only server code can read it. Only the plugin can write it: a create or update from server code is refused even with `overrideAccess`, and a key in `context` doesn't get past that, because the plugin marks its own writes in an async context private to its modules; a key in `context` such as `hatsInternal` or `hatsDissolving` is ignored. Code that imports the plugin's source files directly could still mark a write; the package doesn't export them. Other plugin collections (`hat-links`, `hat-members`) follow their own access rules, and server code with `overrideAccess` can still change them, as in 0.4.0. Deleting the asker removes their requests; deleting the invited account empties requests to it, which still count toward the asker's limit until they expire.
  - **New option `linkAnswerMs`** (default 2000, from 0 to 2147483647; any other value, or one that isn't a number, refuses to start): every link request answers after this many milliseconds. The records and emails run inside that time; work still running when it's up carries on after the answer and is logged. Keep it above your slowest email send, especially on hosts that stop work once a response is sent.
  - **Behavior changes.** The asker's own confirmation email now comes after the other account confirms. An account can hold `maxLinked × 2` open requests at once (then `tooMany`, 429). `setFull` and the new cap also answer after `linkAnswerMs`. An invitation whose send fails can never be confirmed. A confirmation is refused when it would take the set past `maxLinked`, when the account joined another set meanwhile, or when the asker's set changed since the request (a set the asker started from another of their own requests is allowed). Approving past `maxLinked` is refused too. Two confirmations of one token at once get one success and the expired-link page. Unlinking another account that hasn't confirmed answers `notInSet`, as it isn't shown. The `link-requested` event's `link` is always a set that exists.
  - **When link events fire.** `link-requested` fires at ask time only when the asker is already in a set, after the invitation is sent, and its `req` is the asker's request. An asker with no set gets no event at ask time: `link-requested` fires when the invited account confirms, just before `link-confirmed`, and its `req` is that confirming request, so `req.user` is whoever is signed in on that browser. That is often nobody, and can be the invited person, who may be a child. `by` is always the asker and `account` the invited account. A request that sends no invitation fires nothing. `link-confirmed` fires once the confirmation's records are written.
  - **A failing or slow `onEvent` handler can't break a confirmation.** If the handler throws on `link-requested` or `link-confirmed`, the confirmation still finishes with its page, its records stay written, `link-confirmed` still fires, and the error is logged by its name only (a message can carry details about the people involved). Only a short plain name is logged (a letter, then up to 39 letters, digits or underscores); any other name, or a name that throws when read, is logged as `Error`. The page waits at most 2 seconds for each of those two events; a handler still running after that carries on unwaited, and a warning is logged. The same holds for `link-requested` at ask time. The event's shape is the same as 0.4.0's.
  - **The site's callbacks run without the plugin's mark.** `confirmURL`, `sendEmail` and `onEvent` (including `sessions-revoked`, which can fire inside the plugin's own deletes) are called with the plugin's mark off the request, so a write the site makes from them is checked like any other server write. The mark lives in an async context, so it holds only for the plugin's own code and what that code awaits: a callback that calls back into the plugin, or one still running after the plugin moved on, never leaves the mark on or sees it.
- **Event handlers can't block or undo a change that happened.** Every `onEvent` call (`sessions-revoked`, `unlinked`, `link-requested`, `link-confirmed`) now goes through one path: a handler that throws is logged by its safe name and skipped, and one still running after 2 seconds is left to finish unwaited. In 0.4.0 a throwing `sessions-revoked` or `unlinked` handler turned an unlink or an account delete into an error, and with a transaction undid it, so a child's account could fail to delete. `switched` and `link-approved` are unchanged.
- **A database failure is never reported as success.** In the clean-up after an account delete, while an unlink dissolves a set, and in an approver's delete of a member row, every bulk delete or update the plugin runs now throws when Payload reports a row it couldn't remove or change. The call answers with an error. A single delete or unlink with a transaction is undone; in a bulk delete, or without a transaction, the account can be deleted with some of its link rows left, and sessions through it stay refused. The expiry sweep of old requests stays best effort and logs a warning.
- **A switched session is refused once the account it was switched through is gone.** On each request a switched session checks that its signed-in account still exists; if not, it's ended and the request is signed out. This covers a delete whose clean-up failed part way without a transaction, which 0.4.0 also left acting as the other account.
- **Site and other plugins' hooks run without the plugin's mark.** At startup the plugin wraps every hook and field hook on every collection and global, and the config-level hooks, except its own, so code that runs inside the plugin's writes (another plugin's hook on `hat-members`, a users read hook, a field's afterRead) can't write `hat-requests`.
- **MongoDB indexes stay as 0.4.0 built them.** The account on `hat-members` and the asker on `hat-requests` stay `required` on MongoDB, so `hat-members.user_1` stays a plain unique index and a site with `ensureIndexes: true` starts on a 0.4.0 database with no host step. Only SQL adapters relax NOT NULL, and the plugin still requires both on every write there.
- **Unlinking takes only an exact account id.** `POST /hats/unlink` accepts the id as a string or a number written exactly as the account's id (no leading zeros, spaces, exponents or extra characters, no objects or arrays); anything else is `notInSet` (404), before any database query, so no database error text comes back. The `unlinked` event carries the exact id. Switching takes only an exact id too: anything else, including the text `null`, is `notLinked` (403), the reason switch already gives for any account that isn't linked (on SQLite `null` was a 500 before). A member row with no account never matches anyone.
  - **Linking works on SQL databases.** 0.4.0 and the earlier 0.4.1 work wrote the account's id into link records as a string. On SQLite and Postgres ids are numbers by default, Payload refused those writes, and no link request ever sent an invitation (the asker still got the usual answer, so it failed closed). Ids are now written in the account collection's own id type everywhere a relationship is written: requests, sets and member rows. 0.4.0 has this bug too.
  - **Deleting an account works on SQL databases, and only a delete that happens changes link records.** After an account is deleted, the plugin removes its member rows (dissolving a set left with one account), removes its own requests, empties requests to it, and clears it as who started a set (with the set's label, which named it) and who added or approved a row. This runs in the users `afterDelete`, placed before the site's own afterDelete hooks, inside the delete's transaction where there is one. So a delete that doesn't happen (refused by access or another plugin's `beforeDelete`, or a document of a bulk delete that fails before its database delete) changes no link records, with or without transactions. Payload deletes a bulk delete's documents side by side; the plugin's clean-up runs one account at a time, so deleting several accounts of one set together leaves nothing behind. On SQL, `hat_link_members.user_id` and `hat_requests.requested_by_id` are now nullable, so the foreign key can set them to null during the delete; the plugin removes those rows straight after, and the plugin still requires both on every write. If the site's own afterDelete throws, a transaction undoes the whole delete; without one the account is gone and the plugin's rows are already cleaned. If the database fails during the clean-up itself, the delete answers with an error: with a transaction a single delete is undone; in a bulk delete, or without a transaction, the account is gone, some of its rows can be left, and sessions switched in through it are refused (see below). On 0.4.0, deleting a linked account on SQLite fails (confirmed by running it), and a link request there answers 202 but writes no rows and sends no email.
  - **Limits.** With Mongoose's `autoIndex` off, the unique index on `holds` has to be built by hand, and until it is, several requests arriving together can each send an invitation; the plugin doesn't check for the index at startup. Calling the link endpoint's handler inside a transaction your own code opened isn't supported: when the claim is refused the database ends that transaction and the request's record goes with it. Any signed-in person can hold an account's one open invitation until it expires (`confirmHours`, 24 by default), so a stranger's request delays everyone else's invitations to that account; the invited person ignores it or lets it lapse.

**Upgrading from 0.4.0** with linking on. Approved sets carry on as they are: listing, switching and unlinking are unchanged. Requests still pending from 0.4.0 complete through their old links and still need both confirmations and an approval; an expired one shows the expired-link page, which says to ask again, and asking again works. What a host does:

1. Regenerate types (`payload generate:types`) for the new `hat-requests` collection. On MongoDB nothing else is needed, and the 0.4.0 indexes stay as they are, so `ensureIndexes: true` starts as before: Payload builds the collection's indexes, including the unique one on `holds`, when it starts. If you've turned Mongoose's `autoIndex` off, build them yourself before link requests are made.
2. On a SQL adapter (Postgres, SQLite), create and run a migration: `payload migrate:create`, then `payload migrate`. It adds the new `hat_requests` table, which has a unique `holds` column and foreign keys to the users table, and drops NOT NULL from `hat_link_members.user_id` (and `hat_requests.requested_by_id`), so deleting a linked account works. Push mode can't move a 0.4.0 SQLite schema, so use the migration there too. Linking never worked on SQL in 0.4.0, so there are no 0.4.0 requests to carry over there.
3. Check custom client wording: a `reasons.linkSent` override that names the address or promises an email to it no longer fits. Status codes and reasons are unchanged; the 202 now takes `linkAnswerMs` (2 s by default), and the plugin's own `LinkedAccounts` keeps its button busy meanwhile.
4. Check an `onEvent` handler that reads `req.user` on `link-requested`: for an asker with no set it now runs on the confirming request, where `req.user` may be nobody or the invited person. Use `by` for the asker.
5. Key `limit` by the address as well as the person, so many accounts can't each ask for one address.

New export: `REQUESTS`. No option was removed or renamed.

Every host-visible change from 0.4.0, in one list (MongoDB needs no database step: its indexes are the ones 0.4.0 built): regenerate types for `hat-requests`; a SQL migration for its table; `reasons.linkSent` wording; `onEvent` `link-requested` uses `by` for the asker and may run on the confirming request; key `limit` by address too; link requests answer after `linkAnswerMs` (new option); new export `REQUESTS`; startup refuses a config that already has a `hat-requests` collection; `context.hatsInternal` is no longer honored as the plugin's mark; with `autoIndex` off, build the `holds` index by hand; `onEvent` waits at most 2 seconds per link event and logs only a safe error name; `confirmURL`, `sendEmail` and `onEvent` run without the plugin's mark; `context.hatsDissolving` is ignored too; `linkAnswerMs` outside 0 to 2147483647 (or not a number) refuses to start; link records hold the account's own id type, so on SQL linking and account deletes now work; the users `afterDelete` hook the plugin adds now runs before the site's own afterDelete hooks (0.4.0 put it after), and it now also removes the account's requests, empties requests to it and clears it from sets and member rows; on SQL the migration also makes `hat_link_members.user_id` and `hat_requests.requested_by_id` nullable; a throwing or slow `onEvent` handler is logged and skipped for every event except `switched` and `link-approved`, so an `unlinked` or `sessions-revoked` handler error no longer fails an unlink, an approver's delete or an account delete; `POST /hats/unlink` and `POST /hats/switch` take only an exact id; site and other plugins' hooks run without the plugin's mark, so they can't write `hat-requests`; a database failure during the clean-up after an account delete, an unlink or an approver's member delete now fails that call; a switched session is refused once its signed-in account is gone; SQLite push mode can't move a 0.4.0 schema, so use a migration.

## 0.4.0 (2026-11-26)

- **`switchSession(req, { account, hat, code })`.** A site's own route can switch the signed-in person without the picker. The body of `POST /hats/switch` moved into one shared function that the endpoint and `switchSession` both call, so they can't drift. It acts only for `req.user` (refused with `signIn` when nobody is signed in), has no option that skips a check, and returns `{ ok: true, account, hat, cookie }` or `{ ok: false, status, reason, message }` with the endpoint's reasons, `needsCode` included. An error from a site hook, or any unexpected error, is a refusal (`failed`, 500), never a pass. The endpoint answers as before (the Payload error shape, and 401 `needsCode` with its body); the one visible change is that a missing Payload session now carries the reason `noSessions`. New exports: `switchSession`, `SwitchResult`, `SwitchInput`.
- **Same-origin POST only, enforced.** SameSite=Lax sends the cookie on a top-level GET, so a link on another site could switch someone silently while a code is still remembered. The shared switch now refuses unless `req.method` is POST (`notPost`, 405), when an `Origin` header is present and isn't the site's own origin, and when `Sec-Fetch-Site` is present and isn't `same-origin` (`crossSite`, 403). The README says to set Payload's `csrf` list too.
- **A locked account can't be switched into.** An account whose `lockUntil` is in the future is refused (`locked`, 403), as direct sign-in refuses it. This also fixes the endpoint, which allowed it before.
- **Fails closed on headers.** Plain-object headers are read case-insensitively. No headers, or anything that is not a Headers instance or a plain object of strings (an array, a Map, an object with a get()), is refused (`crossSite`).
- **Unverified accounts** (`_verified: false` with `auth.verify` on) are refused (`unverified`, 403), as direct sign-in refuses them.
- **README sample** is now a working route.
- **One code per sitting.** `stepUp.rememberPer: 'set'` (added in 0.2.0) with a gain-based `stepUpWhen` is the supported way: one code covers the person's set for `rememberMinutes` (default 180), then it asks again. Documented, and now tested with the expiry and `rememberMinutes`. Switching back down to the signed-in account asks for no code.

Tested: 21 new tests (12 for the switch itself, then 9 for the changes above: GET, missing method, foreign Origin, cross-site and same-site Sec-Fetch-Site, GET with both, own origin allowed, locked account, and the users-collection check on its own), each refusal through `switchSession` and the endpoint with the same status and reason (and the same call passing once the guard is lifted); no user; a user with no browser session; the endpoint and the function giving the same cookie attributes and session effects; ignored skip options; throwing `verify`, `available`, `blocked`, `stepUpWhen`, `showSwitch` and `hatsOf`; the set remembered across accounts, 179 and 181 minutes, `rememberMinutes` 30; back to the signed-in account with no code; refusal while blocked and after an unlink. The new tests fail before the change (`switchSession` missing) and pass after. Full suite 114 passing (plain-object and missing headers, unverified account added), typecheck and build clean. Not tested: a real browser or site route (requests are built by hand, with headers set directly; Origin behind a proxy that rewrites the URL isn't tried), the README sample (it's checked by eye and by typecheck of the same calls, not run), and a throwing `onEvent` (it runs after the switch and is reported as a failed switch, with the session already moved).

## 0.3.0 (2026-11-20)

- **A new hat switch.** A pill trigger ("Acting as Author"), a 360 px popover on wide screens and a bottom sheet under 640 px. It shows the hat worn now, then one fieldset per account (current account first) with a button per hat (`aria-current` on the one worn): safe hats first, then hats that ask for a code, tagged with a lock and Needs a code. Safe hats switch in one tap; the others open a code screen (Confirm it's you, Switch to <hat>, Cancel, and an optional Use another way). A Back to Member row stays at the bottom above the narrowest hat. Escape, close and the scrim return focus to the trigger, Cancel returns it to the hat, and focus stays in the panel while it's open.
- **A note after each switch.** "Now acting as <hat>. Switch back to <narrowest hat>." in a status region, kept in sessionStorage across the reload. A note with a Switch back link stays until it's dismissed and focus stays put; one without goes after 5 seconds (longer while hovered or focused), with focus moved to the new page's heading. `HatsSwitchedNote` shows it on pages without a switch.
- **Site options on `HatSwitcher`:** `accountTitle`, `hatHelp`, `orderHats`, `anotherWay` and `noteMs`, with defaults that need none of them. New exports: `HatsSwitchedNote`, `defaultOrder` and their types. New `text` keys for every new word; the old keys stay.
- **Review fixes on the switch.** Buttons replace radios, so a tap that switches is no longer a checked radio that follows the arrow keys. The Switch back note stays until dismissed. Focus lands inside the panel even with no current hat. A pasted "123 456" or "123-456" code keeps all its digits (spaces and dashes are dropped, no length cap). The scrim closes on click, so the tap doesn't reach the page. The code field's border uses `--hats-field` (default elevation 600) for 3:1 contrast. Hat help is read once. Escape on the code screen goes back to the list and keeps the typed code. A hidden status line says Switching… while a switch runs. ## 0.2.0 (2026-11-16)

- **`stepUpWhen`.** Decides whether a switch needs a code, in place of the hat's `sensitive` flag. It gets `from` and `to` (user as worn, and hat), so a site can ask only when the new hat holds a role or permission the current one doesn't. Only an exact `false` skips the code; `true`, a throw or any other answer asks. The `GET /hats` menu's `needsCode` follows the same rule. Without it, nothing changes.
- **`stepUp.rememberPer: 'set'`.** One good code is remembered for every account in the same linked set, for `rememberMinutes` (default 180). Default `'account'` is unchanged. An account in no set is remembered on its own.
- **`stepUp.available` and `stepUp.verify` receive `signedIn` and `set`.** `signedIn` is the account that actually signed in, `set` is the linked set's id or `null`. `user` is still the target. `available` gets them as a second argument. The `switched` event's `steppedUp` still means a code was given in that request. New type export `StepUpContext`.

Tested: 34 tests (30 server, 4 client) against a real Payload and an in-memory MongoDB; the existing tests pass unchanged. New ones cover step down, up and sideways, `stepUpWhen` throwing, rejecting and answering `'yes'`, `1`, `{}` and `undefined`, the menu agreeing with the switch, one code across a linked set inside and after the 3-hour window, an account in no set, and what `available` and `verify` are told. Two mutation checks (set memory off, `stepUpWhen` accepting only `true`) each fail a test.
Not tested: the React components with the new options (they only read `needsCode`); a real authenticator.

## 0.1.5 (2026-11-11)

- **`limit` and `blocked` fail closed.** `limit` must answer exactly `true` to allow a link request; any other truthy answer is now refused with `tooMany` (429), as a throw already was. A `blocked` that throws, or answers anything but a reason or `null`, now refuses switching, linking and unlinking with 409 `blocked` and a general reason. Before, a throw escaped as a 500. Tested: 26 tests (22 server, 4 client), 5 mutation checks.

## 0.1.3 (2026-11-10)

- **A session with nothing left to wear is signed out.** If a site's `hatsOf` gives an account no hats at all (for example, because the site disabled it), a session the plugin keeps a record for, one switched in from another account or one wearing a hat, is now revoked and signed out. Before, with no hat to narrow to, it was handed the account with every role. A plain sign-in with no record is unchanged: refusing a disabled account at sign-in is the site's job.

Tested: 22 tests (18 server, 4 client). The new test, which disables an account with a direct write so no hook runs, fails without the change.

## 0.1.2 (2026-11-10)

Security fixes from a review of 0.1.1.

- **A revoked session stays signed out.** Payload writes an account's whole list of sessions at once, so a sign-in at the same moment as a revocation could write the revoked session back. Its record had already been deleted, so it then looked like a plain sign-in with every role. Records are now kept, marked `revokedAt`, and a session with one is signed out (and taken off the account again). This covers unlinking, an approver's delete, a lost role, a deleted account, signing out, and the session left behind when switching accounts.
- **Old session records are cleaned up**, at most 50 per switch: only those that expired over a day ago and whose Payload session is gone, so a session Payload kept alive keeps its hat. `cleanupSessions` is exported for a site's own job.
- **`wear()` must narrow.** A `wear()` that returns the user object unchanged is refused, so a site's mistake can't quietly leave every role on.
- **`limit` option** for link requests, called with the acting account and the email. A no, or a limit that fails, refuses with `tooMany` (429) and sends nothing.

Tested: 21 tests (17 server, 4 client). The new tests include a revoked session written back into the account (it stays signed out; this test fails without the fix), clean-up keeping a refreshed session's record, the `wear()` guard, and the limit refusing (and failing closed). Not yet tried on a site.
